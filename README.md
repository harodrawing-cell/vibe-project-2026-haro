## 3. 규칙 우선순위와 적용 범위

1. 사용자로부터 받은 **현재 작업 지시와 수정 허용 범위**
2. 승인된 프로젝트 PRD·화면 디자인·콘텐츠·기능 명세
3. 현재 프로젝트에서 확인되어 정상 동작하는 HTML·CSS·JS 구조와 디자인 시스템
4. `spec-kit/HARO_SpecKit.md`의 공통 Designer·Developer 규약
5. 일반적인 웹디자인·웹개발 관행

- Spec Kit의 **HARO 실소스 분석값은 해당 레퍼런스/재현 작업에만 적용**합니다. 다른 사이트의 색상·폭·브레이크포인트에 무조건 복사하지 않습니다.
- 신규 개발과 기존 사이트 수정의 반응형·코드 전략을 구분합니다. 기존 코드가 Desktop First라면 사용자 요구가 없는 한 임의로 Mobile First로 전환하지 않습니다.
- 규칙이 충돌하거나 접근성·보안에 중대한 문제가 있다면 충돌 사유와 최소 변경안을 명시합니다.

## 4. 모든 작업의 필수 보호 규칙 — MUST

- 요청하지 않은 섹션, 콘텐츠, 디자인, 파일, 기능을 삭제·변경·추가하지 않습니다.
- 기존 클래스명·ID·앵커·CSS 변수·JavaScript 이벤트·`data-*` 연결을 확인 없이 변경하지 않습니다.
- 실제 파일 존재 여부를 확인하지 않은 이미지·폰트·JSON·외부 링크를 임의 생성하지 않습니다.
- 동일 기능의 스크립트를 중복 추가하거나 전역 변수·상수를 재선언하지 않습니다.
- 사용자가 요청하지 않은 프레임워크, 라이브러리, CDN, 빌드 도구를 도입하지 않습니다.
- 화면이 깨지는 문제를 원인 분석 없이 `!important`나 `overflow-x: hidden`으로 가리지 않습니다.
- 테스트하지 않은 기능을 **정상 동작 / 검증 완료**라고 보고하지 않습니다.
- 작업 전 기존 파일을 보존하고, 변경 사항은 검토 가능한 최소 단위로 유지합니다.

## 5. 디자인·개발 시 확인할 사항

**Designer 관점:** 색상·폰트·간격 토큰, 시각적 위계, Figma/참조 이미지 대응, Desktop·Tablet·Mobile 레이아웃 차이, 이미지 비율·잘림, 버튼 및 컴포넌트의 상태, 애니메이션과 움직임 줄이기 설정.

**Developer 관점:** 시맨틱 HTML, CSS 역할별 분리·명명 일관성, 적절한 반응형 미디어쿼리, 키보드·ARIA 접근성, JavaScript 초기화와 이벤트 생명주기, 파일 경로, 성능·보안, 기존 기능 회귀 여부.

자세한 수치와 금지·예외 규칙은 **Spec Kit 원문**을 따릅니다.

## 6. 작업 실행 순서

- **이번 작업 목표:** 무엇을 완성하거나 고쳐야 하는가?

- **보존 대상:** 어떤 기존 기능·스타일·경로는 유지할 것인가?
- **확인 필요:** 제공되지 않은 자료나 아직 검증되지 않은 항목은 무엇인가?
