## 0. AI Agent의 기본 역할과 지시 체계

이 문서는 프로젝트의 **Designer 규약과 Developer 규약을 하나로 통합한 실행 기준**이다. AI는 한 화면의 모양만 구현하는 작업자가 아니라 정보 구조, 시각 일관성, 접근성, 반응형 동작, 코드 안정성, 성능, 보안, 검증까지 책임지는 시니어 리드로 행동한다.

### 0.1 규칙의 강도

- **MUST / 필수:** 반드시 지킨다. 충족하지 못하면 완료로 보고하지 않고 미충족 내용을 명시한다.
- **SHOULD / 권장:** 합리적 이유가 없는 한 준수한다. 예외는 이유를 보고한다.
- **MAY / 선택:** 요구사항과 실익에 따라 적용한다.
- **금지:** 기존 코드의 무단 삭제·전면 재작성, 범위 밖 리디자인, 임의 자료·링크·이미지 대체, 테스트 미실행 상태에서의 성공 주장.

### 0.2 우선순위

1. 현재 작업에 대한 사용자의 명시적 요구사항과 수정 허용 범위
2. 승인된 PRD·기능 명세·화면 시안·실제 콘텐츠
3. 현재 프로젝트에서 이미 검증된 HTML 구조, CSS 아키텍처, JS 구현 방식, 디자인 토큰(사용자 제공 HARO 소스 분석 시 PART D 참조)
4. 본 `spec-kit/HARO_SpecKit.md`
5. 현재 작업에 해당하는 `spec-kit/AGENTS.md` 공통 규칙
6. 일반적인 디자인·개발 관행

충돌이 발생하면 기존 기능을 보호하는 **최소 변경안**을 선택하고, 보안·접근성 등 중요한 위험은 숨기지 않고 기록한다. 정보가 일부 부족하더라도 진행 가능한 범위까지 작업하며, 불확실한 값은 추정 또는 미확인으로 표기한다.

`spec-kit/AGENTS.md`의 PART 3은 Discovery Expedition 웹사이트 고유 규약이다. HARO 작업에는 적용하지 않는다. AGENTS의 PART 1·2 공통 규칙도 승인된 HARO 명세나 현재 동작과 충돌하면 기존 구조를 무단으로 바꾸는 근거가 될 수 없다. `README-1.md`의 레이아웃·색상·타이포그래피 예시 역시 해당 Discovery Expedition 프로젝트에 한정한다.

### 0.3 절대 금지 사항

1. 승인 없이 섹션·콘텐츠·기능·이미지를 추가하거나 제거하지 않는다.
2. 특정 구역만 수정하라는 지시를 전체 페이지 리디자인 또는 전면 리팩터링으로 확대하지 않는다.
3. 기존 클래스명·ID·경로·파일명을 이유 없이 변경하지 않는다.
4. 실제 존재 여부를 확인하지 않은 이미지·JSON·API·외부 URL을 확정값으로 쓰지 않는다.
5. 동일 기능의 JS를 중복 추가하거나 같은 전역 `const`/`let`을 재선언하지 않는다.
6. `href="#"` 같은 임시 링크를 최종 완성 기능처럼 보고하지 않는다.
7. 오류를 덮기 위해 `overflow-x: hidden`, `!important` 등을 무분별하게 적용하지 않는다.
8. 실제 실행하지 않은 테스트를 통과했다고 말하지 않는다.
9. 사용자가 요청하지 않은 프레임워크·라이브러리·CDN·빌드 시스템을 설치하지 않는다.
10. 실제 콘텐츠, 디자인 수치, 접근성·성능 결과를 확인 없이 만들어 내지 않는다.

## 1. 모든 작업에 적용되는 표준 절차

### 1.1 작업 전 점검(Preflight) — MUST

1. 프로젝트 목표, 주요 이용자, 핵심 행동(CTA), 현재 요청의 완료 기준을 확인한다.
2. HTML 엔트리 파일, 연결 CSS/JS, 이미지·폰트·JSON 폴더 및 배포 환경을 확인한다.
3. 수정할 섹션과 관련 ID·클래스·앵커·이벤트·반응형 미디어쿼리를 추적한다.
4. 제공된 화면 시안이 있으면 데스크톱·태블릿·모바일 간 변화점을 분석한다.
5. 기존 컴포넌트, 디자인 토큰, 파일 네이밍, 스크립트 초기화 방식을 확인한다.
6. **변경할 파일·구역 / 그대로 유지할 파일·구역 / 회귀 위험**을 구분한다.
7. 누락된 자산과 확인된 자산, 관찰값과 추정값을 구분한다.

### 1.2 구현 순서 — MUST

`요구사항 이해 → 기존 코드 및 자료 분석 → 수정 범위 설정 → 디자인·반응형 상태 정의 → HTML 구조 → CSS 표현 → JS 동작 → 검증 → 변경 결과 보고`

- 기존 파일을 수정하는 경우 필요 부분만 수정한다.
- 코드가 큰 경우 위험한 변경을 작고 검증 가능한 단위로 나눈다.
- 이미 동작하는 기능이 있으면 새로 만드는 대신 기존 구현을 보완한다.
- 사용자 요청이 HTML 수정과 파일 제공이라면 **수정된 완전한 파일 또는 적용 가능한 정확한 패치**를 전달한다.

# PART A. DESIGNER RULES — 웹디자인 및 UX/UI 규약

## 2. UX/UI 설계 원칙

**DES-001 | 목적 우선:** 장식보다 사용자의 정보 탐색과 행동을 먼저 설계한다. 화면마다 주요 행동이 명확해야 한다.

**DES-002 | 일관성:** 헤더, 메뉴, 버튼, 카드, 탭, 모달, 폼의 모양과 동작을 공통 컴포넌트로 관리한다.

**DES-003 | 시각적 위계:** 제목 → 설명 → 행동 요소의 구분이 크기·여백·위치만으로도 성립해야 한다.

**DES-004 | 예측 가능성:** 똑같이 보이는 요소는 똑같이 작동한다. 비활성 요소를 클릭 가능한 것처럼 꾸미지 않는다.

**DES-005 | 실제 콘텐츠 검수:** 한글 길이, 숫자·날짜, 긴 영문, 줄바꿈, 동적 데이터 등 실제 표시 조건으로 확인한다.

**DES-006 | 최소 변경:** 기존 사이트 수정 시 요청한 구역 외 색상·폰트·간격·이미지·애니메이션을 바꾸지 않는다.

**DES-007 | 구현 가능성:** 각 시각 요소마다 HTML 구조, CSS 구현, 원본 자산, JS 상호작용이 설명 가능해야 한다.

## 3. 디자인 시스템과 토큰

색상·폰트·간격·크기·그림자·모션을 **프로젝트 공통 토큰**으로 관리한다. 기존 토큰이 있다면 변수명을 유지하고 새 토큰의 무분별한 생성을 피한다.

| 범주 | 권장 변수 예시 | 필수 판단 기준 |
|---|---|---|
| 색상 | `--color-brand`, `--color-text`, `--color-bg`, `--color-border` | 의미 있는 명칭, 대비 확보 |
| 타이포 | `--font-family-base`, `--font-size-*`, `--line-height-*` | 한글 가독성, 제목 계층 |
| 간격 | `--space-1` ~ `--space-8` | 반복 가능한 간격 척도 |
| 레이아웃 | `--container-max`, `--gutter`, `--section-space` | 고정 최대 폭 + 유동 폭 |
| 도형 | `--radius-*`, `--shadow-*`, `--border-width` | 일관된 시각 언어 |
| 모션 | `--duration-fast`, `--duration-base`, `--ease-standard` | 목적이 있는 움직임 |
| 레이어 | `--z-header`, `--z-dropdown`, `--z-modal` | 명확한 쌓임 순서 |

### 3.1 타이포그래피 — MUST

- `h1`~`h6`, 본문, 보조문구, 버튼의 크기·두께·행간·자간을 계층화한다.
- 본문은 가독성을 우선한다. 신규 디자인은 약 16px를 시작점으로 검토하되 확정값은 PRD가 우선한다.
- 한글·영문·숫자 혼합 문구, 글꼴 폴백 및 200% 확대 시 읽기 쉬워야 한다.
- 중요한 문구는 가능한 이미지에 합성하지 말고 HTML 텍스트로 표현한다.
- 강제 `<br>`는 의도된 문장 구분에만 사용하고 반응형에서 무너지는 경우 CSS/마크업을 조정한다.

### 3.2 컬러와 대비 — MUST

- 일반 본문 텍스트와 배경 대비: **4.5:1 이상**을 기본 목표로 한다.
- 큰 텍스트의 대비: **3:1 이상**을 기본 목표로 한다.
- 의미 있는 아이콘·입력 경계 등 비텍스트 UI: 적용 기준에 따라 **3:1 이상**을 목표로 한다.
- 오류·성공·선택 상태를 색상만으로 전달하지 않고 문구·모양·아이콘을 병행한다.
- 최종 접근성 준수 여부는 예외와 전체 화면을 검토해 판단한다.

## 4. 반응형 디자인 — MUST

**DES-101 | 축소가 아니라 재배치:** 데스크톱 시안을 작은 화면에 통째로 줄여 넣지 않는다. 정보 우선순위에 맞춰 컬럼, 순서, 간격, 크롭을 조정한다.

**DES-102 | 전략 존중:** 신규 프로젝트는 Mobile First(`min-width`)를 기본으로 한다. 기존 프로젝트가 Desktop First(`max-width`)를 사용한다면 **기존 방식 유지**를 우선한다.

**DES-103 | 브레이크포인트:** 콘텐츠가 깨지는 지점을 기준으로 정한다. `390, 768, 1024, 1440px`은 테스트/디자인 참조 폭이지 의무적인 미디어쿼리 값이 아니다.

**DES-104 | 유동 구조:** `max-width`·%·Flex/Grid·`clamp()` 등의 유동 규칙으로 설계한다. 고정폭 아트워크는 크기 변경·재배치·숨김 정책을 명시한다.

**DES-105 | 화면별 상태표:** Desktop / Tablet / Mobile의 배치, 노출 여부, 텍스트 크기, 이미지 잘림, 인터랙션을 기록한다.

**DES-106 | 경계값:** 320px 소형 모바일, 200% 확대, 가로모드, 1920px 대형 화면, 브레이크포인트 전후 폭을 검토한다.

**DES-107 | 모바일 터치:** 주요 터치 대상은 디자인 권장값 **44×44 CSS px 수준**을 먼저 검토한다. 이는 WCAG 2.2 AA의 최소 타깃 크기 기준(예외 포함)과 구별한다.

### 4.1 반응형 상태표 템플릿

| 요소 | Desktop | Tablet | Mobile | 검증 포인트 |
|---|---|---|---|---|
| Header | 전체 메뉴 | 간격 최적화 | 햄버거·모바일 CTA | 열림·닫힘·포커스 |
| Hero | 다열 텍스트·그래픽 | 그래픽 축소·재배치 | 한 열·우선순위 조정 | 잘림·겹침 |
| Card Grid | 2~3열 | 2열 | 1열 | 텍스트 길이 |
| 장식 이미지 | 원본 의도대로 | 기준 좌표 재설계 | 축소 또는 숨김 | 핵심 정보 보존 |

> 표는 일반 예시다. 실제 제작 시 제공 이미지·PRD의 상태에 맞춰 수정하며, 예시를 확정 요구사항으로 취급하지 않는다.

## 5. 이미지·그래픽·애니메이션

- **DES-201 | 소스 매칭:** 사용자 제공 자산을 우선 사용하고 실제 파일명·확장자·대소문자를 확인한다.
- **DES-202 | 해상도:** 비트맵 화질과 고해상도 화면을 고려한다. 단순 로고·도형은 SVG 사용을 검토한다.
- **DES-203 | 크롭:** `object-fit`/`object-position`을 명시하고 화면별 인물·캐릭터의 주요 부위가 잘리지 않는지 확인한다.
- **DES-204 | 콘텐츠 분리:** 중요한 문구는 HTML, 장식은 CSS/SVG/이미지로 분리하는 것을 우선한다.
- **DES-205 | 레이어 기준:** 캐릭터·구름·별처럼 절대배치 자산은 기준 부모와 좌표·크기를 명시한다.
- **DES-206 | 클릭 보호:** 장식이 CTA를 가리거나 클릭을 막지 않게 한다. 숨긴 장식 때문에 의미 있는 정보가 사라지면 안 된다.
- **DES-207 | 모션:** 애니메이션은 이해를 돕는 범위에서 사용하고 `prefers-reduced-motion`을 지원한다.
- **DES-208 | 사용 권한:** 이미지·폰트·영상·아이콘의 라이선스와 사용 가능 범위를 확인한다.

## 6. 컴포넌트 상태 설계

가능한 상태에 대해 **기본 / hover / focus / active / disabled / loading / error / success**를 정의한다.

1. **헤더:** 스크롤 다운 시 숨김, 업 시 표시, 배경 전환, 모바일 메뉴, 현재 메뉴, 키보드 탐색, 메뉴 닫기 정책.
2. **버튼·링크:** `button`은 동작, `a`는 이동. hover가 유일한 정보 전달 수단이 되지 않게 한다.
3. **탭·아코디언:** 선택·펼침 상태, 연동 콘텐츠, 키보드/ARIA 상태를 정의한다.
4. **모달:** 열기, 닫기, Escape, 초점 이동·복귀, 배경 스크롤, 외부 클릭 정책을 정의한다.
5. **폼:** 레이블, 필수 입력, 설명문, 오류·제출 상태를 정의한다.
6. **뉴스·카드:** 실제 주소/기능이 있는 경우에만 클릭 가능하게 표현한다. 가짜 링크는 최종 승인 불가.

## 12. Vanilla JavaScript 구현 규칙

- **DEV-401 | 기능별 분리:** 메뉴, 탭, 아코디언, 스크롤, 모달 등의 로직은 책임별로 설계한다.
- **DEV-402 | 전역 변수 충돌 방지:** 중복 전역 `const`/`let` 선언을 금지한다. 기존 방식에 따라 ES Module 또는 IIFE를 적용한다.
- **DEV-403 | 초기화:** `defer`·모듈·DOM 준비 상태를 고려하며 해당 노드가 없는 페이지에서도 다른 기능이 중단되지 않게 한다.
- **DEV-404 | 리스너:** 이벤트를 중복 등록하지 않는다. 동적 목록은 필요 시 이벤트 위임을 적용하고 Observer·타이머를 정리한다.
- **DEV-405 | 상태 동기화:** CSS 클래스, `hidden`, ARIA 값, 실제 표시 상태가 하나의 상태를 반영하게 한다.
- **DEV-406 | 스크롤 성능:** 필요 시 `IntersectionObserver`·`requestAnimationFrame`을 사용하고 강제 레이아웃 반복을 피한다.
- **DEV-407 | 데이터 처리:** JSON 데이터와 렌더링을 분리하고 로딩·빈 결과·에러 UI를 구현한다.
- **DEV-408 | 예외 처리:** 네트워크·이미지·데이터 실패를 적절히 보고하고 배포 코드에 불필요한 디버그 로그를 남기지 않는다.
- **DEV-409 | 실행 보안:** `eval`, `new Function`, 문자열 인라인 이벤트, 신뢰하지 않는 HTML 직접 삽입을 금지한다.

### 최소 초기화 예시

```js
(() => {
  const button = document.querySelector('[data-menu-toggle]');
  const menu = document.querySelector('[data-menu]');
  if (!button || !menu || button.dataset.initialized === 'true') return;

  button.dataset.initialized = 'true';
  button.addEventListener('click', () => {
    const wasOpen = button.getAttribute('aria-expanded') === 'true';
    button.setAttribute('aria-expanded', String(!wasOpen));
    menu.hidden = wasOpen;
  });
})();
```

> 위 예시는 중복 초기화 방지의 최소 형태다. 실제 모바일 메뉴에는 Escape, 바깥 클릭, 초점 처리, 스크롤 정책을 필요에 맞게 보완한다.

## 13. UI 동작의 품질 기준

1. **헤더/메뉴:** 스크롤 방향 감지, 모바일 열림·닫힘, 키보드 조작, 메뉴 밖 클릭, 적절한 초점 관리.
2. **탭:** 키보드 탐색, 활성 탭과 패널의 ARIA 상태 동기화.
3. **아코디언:** 버튼·패널 연결, `aria-expanded` 일치, 키보드 작동.
4. **모달:** 초점 진입·순환·복귀, Escape 닫기, 배경 스크롤 정책, 화면 크기별 표시.
5. **폼:** 라벨과 오류 설명, 필수값, 전송/실패/성공 상태. 실제 전송하지 않는 데모는 명시.
6. **스크롤 애니메이션:** 초기 숨김 요소가 JS 실패 시 영구히 보이지 않는 상황을 예방한다.
7. **링크:** 외부 이동/내부 앵커 목적지가 맞는지 확인하고 사용자의 기대와 레이블을 일치시킨다.

## 16. 공통 접근성 승인 기준

**목표: WCAG 2.2 Level AA.** 아래 사항을 점검하지 않았다면 AA 준수 완료라고 주장하지 않는다.

- 키보드만으로 주요 기능을 사용할 수 있다.
- 포커스가 눈에 띄고 고정 헤더·오버레이 아래에 가려지지 않는다.
- 이미지 대체 텍스트와 문서 구조가 의미에 맞다.
- 선택·열림·오류 상태가 색상과 시각 효과에만 의존하지 않는다.
- 텍스트 대비, 입력 UI 대비, 터치 타깃 크기 및 예외를 확인한다.
- 200% 확대·작은 화면에서 콘텐츠가 겹치거나 사라지지 않는다.
- `prefers-reduced-motion`을 존중한다.
- 자동 검사 외에 실제 키보드 탐색과 수동 검증을 병행한다.

## 22. 분석 대상과 확인 범위

> **레퍼런스 자료와 현재 저장소를 구분한다:** PART D의 상세 수치와 동작 후크는 별도로 제공된 HARO 레퍼런스 저장본 및 CSS 분석 기록을 정리한 값이며, 현재 작업 트리의 실제 파일 목록을 뜻하지 않는다. 현재 저장소에는 `index.html`, `css/`의 CSS 6개, `images/`, `document/`, `spec-kit/`가 있다. 현재 `index.html`은 연결된 CSS 6개를 사용하며 JavaScript 실행 파일은 확인되지 않았다. 레퍼런스 분석에서 언급하는 스크립트·CSS·클래스·기능은 현재 파일에서 존재와 동작을 확인하기 전까지 구현 완료로 간주하지 않는다. 현재 파일과 승인된 HARO PRD가 이 분석 기록보다 우선한다.

| 레퍼런스 파일 | 분석 기록에 기재된 역할 | 변경 시 확인할 영역 |

- **확인:** HTML은 HERO → ABOUT HARO → EMOTICON → STORY → GOODS → FOOTER 순서의 단일 페이지이며, 같은 문서 안에 `id=top/about/emoticon/story/goods/contact`가 존재한다.

- **확인:** 마크업에는 `GSAP`, `Supabase`, `content-loader`, `box-interaction`, `scroll-animations`, `goods-carousel`, `main` 등 **9개 스크립트 파일의 참조**가 보인다.

### 22.1 이 프로파일을 적용하는 순서 — MUST

1. 사용자가 준 실제 프로젝트의 폴더 구조와 최신 파일이 위의 **저장된 웹페이지 HTML**과 같은지 먼저 확인한다.
2. 웹페이지 저장본의 `…_files/` 상대경로 및 `.js.다운로드` 확장자를 **운영 사이트의 원래 경로라고 가정하지 않는다**. 파일의 실제 존재 여부와 참조 관계를 다시 매핑한다.
3. HTML/CSS에서 관찰된 값, HTML 주석으로 설명된 의도, JS 구현을 검증한 내용을 혼동하지 않는다.
4. 참조 소스에 문제가 있더라도 그것을 신규 사이트의 표준 규칙으로 복사하지 않는다. **검증된 패턴은 유지, 위험한 패턴은 개선**한다.
5. 사용자의 승인 없이 기존 HARO 페이지 구조, 편집 후크, 타이포·캐릭터 위치를 일괄 재작성하지 않는다.

## 23. 실제 디자인 시스템 추출 — Designer Rules

### 23.1 색상·서체·공통 토큰 (`tokens.css`) — 확인

| 구분 | 실제 변수 | 실제 값/역할 |
|---|---|---|
| 기본 잉크 | `--color-ink` | `#111111` |
| 강한 잉크 | `--color-ink-strong` | `#111827` |
| 보조 텍스트 | `--color-text-secondary` | `#4b5563` |
| 옅은 텍스트 | `--color-text-muted` | `#9ca3af` |
| 테두리 | `--color-border` / `--color-border-strong` | `#e5e7eb` / `#d1d5db` |
| 브랜드 제목 | `--color-brand-title` | `#874e14` |
| 브랜드 태그라인 | `--color-brand-tagline` | `#ceb290` |
| 주요 표면 | `--color-surface-soft/story/goods` | `#f5f5f5` / `#f8fafc` / `#f3f4f6` |
| 기본 글꼴 | `--font-primary` | Pretendard → SUIT → Noto Sans KR → 시스템 sans-serif |
| 강조 글꼴 | `--font-display` | Cafe24Syongsyong → Jua → 기본 글꼴 |
| 간격 척도 | `--space-1`~`--space-11` | `4, 8, 16, 24, 32, 40, 48, 64, 80, 120, 160px` |
| 모서리 반경 | `--radius-sm/md/lg/xl/pill` | `8/16/24/32/999px` |
| 모션 시간 | `--duration-micro/ui/character/landing` | `0.25/0.5/0.8/2s` |
| 모션 곡선 | `--ease-out` / `--ease-pop` | 소스에 지정된 cubic-bezier 프리셋 |

- **HARO-DES-001 / MUST:** 브랜드의 색상·글꼴·간격·라운딩·속도는 우선 기존 `tokens.css`의 값을 사용한다. 같은 뜻의 변수명·숫자 리터럴을 중복 생성하지 않는다.
- **HARO-DES-002 / MUST:** 새로운 상태(예: 선택·오류·호버)의 컬러가 필요하면 기존 토큰으로 표현 가능한지 먼저 확인하고, 필요 시 의미 있는 새 토큰을 별도 추가한다.
- **HARO-DES-003 / MUST:** 접근성 대조 검사를 통과하지 못하는 토큰의 **사용 조합**은 조정한다. 예컨대 `#ceb290` 텍스트/`#f6efe2` 단색 배경은 계산상 약 **1.77:1**, `#9ca3af` 텍스트/흰색은 약 **2.54:1**이므로 일반 본문 용도로 그대로 사용하기 부적합하다. 실제 HERO는 이미지와 그라데이션을 포함하므로 **렌더된 배경 위에서 따로 측정**한다. 기존 색 자체를 무조건 일괄 교체하지 않는다.
- **HARO-DES-004 / SHOULD:** 브랜드 카피의 줄바꿈은 텍스트가 원래 의도한 개행인지, 반응형 강제 줄바꿈인지 구별한다(`white-space: pre-line` 사용 부위 포함). 페이지 복사·편집 기능에서 개행이 손실되지 않아야 한다.

### 23.2 레이아웃 좌표계 — 확인

- 기준 Figma 프레임 폭 **1440px**. 소스의 `.container`는 `max-width: var(--content-max-width)`와 `box-sizing: border-box`를 사용하며, `--content-max-width: 1440px`, 좌우 `--page-padding: 120px`이므로 **안쪽 내용 영역은 1200px**이다.
- `.section`의 상하 패딩 `--section-gap`과 `main > * + *`의 추가 `--section-margin`은 **서로 다른 값이며 합산된다**. 데스크톱 기준 각각 `80px`, `114px`이다.
- HERO 이미지는 `object-fit: cover`, `object-position: center 30%` 및 그라데이션 오버레이를 사용한다.
- 컴포넌트 전용 절대 배치는 **기준 부모의 좌표계** 안에서 관리한다. `left/top/transform`에 Figma 절대좌표를 그대로 복사하면 뷰포트 변경 시 콘텐츠를 침범할 수 있으므로 반드시 상태별 검증이 필요하다.

**HARO-DES-005 / MUST:** `1440px 컨테이너 = 1440px 실제 텍스트 폭`이라고 해석하지 않는다. 컨테이너의 `box-sizing`과 좌우 padding을 반영하여 실내용 폭을 계산한다.

**HARO-DES-006 / MUST:** 기존 공통 `.section` 간격과 형제 섹션 사이 `margin`을 구별하여 새 섹션을 추가한다. 섹션에 임의의 `margin-top`을 또 추가해 간격이 두 배가 되는 것을 막는다.

## 25. 실소스에서 확인된 컴포넌트·인터랙션 계약

### 25.1 클래스·데이터 후크 보존 — MUST

| 구분 | 실제 사용 예 | 보존 이유 |
|---|---|---|
| BEM형 클래스 | `.hero__title`, `.nav__links`, `.story__photo-grid`, `.goods-card__media` | 스타일 영역·요소 책임 유지 |
| 상태 클래스 | `.is-hidden`, `.is-open`, `html.reveal-armed` | JS/CSS의 상태 경계 |
| 연결 데이터 후크 | `[data-box-stage]`, `[data-box-frame]`, `[data-goods-track]`, `[data-goods-prev]`, `[data-goods-next]` | DOM 기능 연결 지점으로 추론됨 |
| 등장 애니메이션 | `[data-reveal]`, `[data-reveal-visible]`, `[data-paw-visible]` | 단계별 등장 및 최종 가시성 |
| 콘텐츠 편집 후크 | `data-edit`, `data-edit-src`, `data-edit-href`, `data-edit-mailto` | 콘텐츠 관리 로직과 연결된 것으로 추론됨 |

- **HARO-DEV-001 / MUST:** 요소를 재배치하거나 HTML을 개선할 때 위 데이터 후크를 임의로 삭제·변경하지 않는다. 변경이 불가피하면 **해당 JS/데이터 모델과 함께 수정하여 동작을 검증**한다.
- **HARO-DEV-002 / MUST:** `data-edit="goods.items.0.title"`처럼 배열 인덱스를 포함한 키는 단순 문자열이 아니라 콘텐츠 매핑 계약으로 취급한다. 상품 순서·개수 변경 시 이미지·이름·링크 키의 정합성을 점검한다.
- **HARO-DEV-003 / MUST:** `index.css` 및 `pretendard.css`의 상대 font URL은 **CSS 파일 기준**으로 해석한다. 파일 위치를 바꾸는 경우 `url(...)` 경로·폰트 실재·fallback·`font-display` 및 라이선스를 점검한다.
- **HARO-DEV-004 / MUST:** 사용자에게 제출할 최종 실행 소스는 `웹페이지 저장본`의 자산 경로를 실제 프로젝트 경로로 정리한다. 다른 파일이 없는데 HTML/CSS만으로 완성됐다고 보고하지 않는다.

### 25.2 HERO 상자 애니메이션 — 확인된 구조 / 실행은 추론

- HTML에 `.box-interaction` / `[data-box-stage]` / `[data-box-frame]`이 있다.
- `box.css` 주석에 12장의 `BOX_001..012.png` 프레임 이미지와 `box-interaction.js` / GSAP 타임라인 연동 의도가 명시되어 있다. 프레임 이미지는 동일한 1024×1024 캔버스 정렬을 전제로 크롭한다.
- HTML에는 시작 이미지로 `BOX_012.png`가 보인다. 실제 초기 재생 상태나 클릭 후 전환은 **JS 미제공으로 미확인**이다.

**HARO-INT-001 / MUST:** 시퀀스 이미지의 **원본 프레임 수·순서·공통 캔버스·정렬 좌표·동일 크롭 영역**을 묶어서 관리한다. 한 프레임만 다른 비율로 크롭해 상자가 튀거나 흔들리지 않도록 한다.

**HARO-INT-002 / MUST:** 클릭 조작은 키보드 Enter/Space로도 가능해야 한다. 현재 HTML은 `div[role="button"][tabindex="0"]`이므로 JS 키보드 이벤트 구현을 확인해야 한다. 신규 구현은 가능한 네이티브 `<button>` 사용을 우선 검토한다. `aria-pressed`는 실제 토글 상태가 있는 컨트롤에만 의미가 맞게 사용한다.

**HARO-INT-003 / MUST:** 이미지 로드 실패, JS 로드 실패, 모션 감소 설정에서도 의미 있는 **정적 대체 이미지와 사용자 안내**가 남도록 한다. 애니메이션 실패가 전체 HERO를 비워두지 않도록 한다.

### 25.3 스크롤 등장 효과 — 확인된 CSS / 실행은 추론

- `layout.css`는 `[data-reveal]` 콘텐츠를 **기본 표시**하고, `html.reveal-armed`일 때만 `opacity:0`/`translateY(20px)`을 적용하도록 설계했다.
- `[data-reveal-visible]` 상태가 되면 다시 나타나는 CSS가 존재한다. `sections.css`의 ABOUT 발자국은 `[data-paw-visible]`와 지연 시간을 별도로 사용한다.

**HARO-INT-004 / MUST:** 등장 효과는 **Progressive Enhancement**로 구현한다. 기능 초기화 전·JS 부재·Observer 미지원·오류·reduced-motion 상태에서 본문 콘텐츠가 사라지지 않아야 한다.

**HARO-INT-005 / MUST:** 초기화 성공 후에만 `reveal-armed`를 켜고, 대상별 등장 상태를 관리한다. 이미 나타난 콘텐츠는 스크롤 역방향에서 반복적으로 사라지지 않는 기존 의도를 보존한다. 단, HTML 저장본에는 `<html class="reveal-armed">`가 이미 기록돼 있어 **정적 내보내기 시 이 클래스를 제거하거나 실패 대비 로직을 별도 검증**해야 한다.

### 25.4 GOODS 캐러셀 — 확인된 CSS / 실행은 추론

- 트랙은 `overflow-x:auto` + `scroll-snap-type:x mandatory` + `tabindex="0"`을 사용한다.
- 좌/우 화살표는 `<button>`, `aria-label`, 끝 위치 버튼에는 `disabled` 속성이 있다.
- `sections.css`는 데스크톱 4개, 860px 이하 2개, 599px 이하 가시 카드 너비 80%로 반응형을 정의한다.

**HARO-INT-006 / MUST:** 터치·트랙패드의 자연 스크롤을 우선 보존하고, 화살표/키보드는 보조 조작으로 연동한다. 버튼 끝 상태는 스크롤 위치와 동기화한다(실제 JS 동작 검증 필요).

### 25.5 내비게이션·외부 CTA

**HARO-INT-010 / MUST:** `OGQ`, Instagram, 굿즈 스토어 등 외부 링크는 실제 목적지를 확인한다. 운영 전 `href="#"` 또는 자기 사이트 `/#` 임시 목적지는 승인 불가이며, 새 탭 동작·레이블·`rel="noopener"` 등을 확인한다.

| P3 | HTML 저장본의 `.imageye-selected` CSS, 정적 `style=...`, 저장 시점 인라인 상태 | 확장 프로그램/런타임이 남긴 코드인지 식별 후 배포 원본에서 정리 검토 |

## 27. 신규 프로젝트로 일반화할 수 있는 패턴

위 레퍼런스를 다른 사이트에 적용할 때는 **디자인 값 복사**가 아니라 **설계 방식 복사**를 기본으로 한다.

1. **토큰 우선:** `tokens.css`를 단일 원천으로 두고 기본 요소/레이아웃/컴포넌트/섹션 CSS를 분리한다.
2. **영역 소유권:** 공통 스타일과 개별 섹션 스타일을 분리해 한 컴포넌트 수정이 다른 섹션을 깨뜨리지 않게 한다.
3. **BEM + 상태 + 데이터 후크:** CSS용 `block__element--modifier`, 시각 상태용 `.is-*`, JS 연결용 `data-*`를 구분하되 실제 프로젝트의 기존 관례를 우선한다.
4. **공통 그리드 + 자체 분기:** 큰 단위 브레이크포인트(예: 토큰)와 콘텐츠 기반 컴포넌트 분기를 공존시킨다.
5. **아트워크 좌표 보호:** 이미지의 원본 캔버스, 크롭, 앵커 위치, 반응형 풋프린트를 명시해 캐릭터의 시각 안정성을 확보한다.
6. **점진적 향상:** 애니메이션/JS 실패 시 텍스트와 핵심 이미지가 남도록 기본 표시 상태를 설계한다.
7. **CSS + JS 상태 계약:** 메뉴/캐러셀/리빌처럼 여러 파일이 제어하는 요소는 클래스·ARIA·JS 초기화를 계약으로 관리한다.
8. **콘텐츠와 코드 분리:** 텍스트·이미지·URL이 관리자나 JSON에서 바뀐다면 데이터 키와 DOM 후크를 명시적으로 유지한다.
9. **스크린샷 역설계 정확도:** Figma 수치뿐 아니라 박스모델, 패딩, 이미지 오버플로, 미디어쿼리 적용 순서로 결과를 검증한다.
10. **증거 기반 완료 선언:** HTML/CSS에서 구조가 확인돼도 JS·이미지·폰트가 없으면 실행 완료를 주장하지 않는다.

## 30. 규약 통합·충돌 처리 프로토콜 — MUST

**INT-001 | 문서 통합:** 이 문서가 HARO 프로젝트의 통합 규약이다. `spec-kit/AGENTS.md`는 별도의 보완 문서이며, 공통 규칙 중 충돌 없이 적용할 내용만 참고한다. 해당 파일의 Discovery Expedition 전용 PART 3은 HARO에 적용하지 않는다. 규칙이 충돌하면 0.2절 우선순위를 따르고 관련 명세를 무단으로 덮어쓰지 않는다.

**INT-002 | MUST/MUST NOT/SHOULD:** MUST·MUST NOT은 프로젝트에 적용되는 필수·금지 조건, SHOULD는 이유가 있을 때 예외 가능 조건으로 구분한다. 사용자 승인·기존 코드와 충돌 시 0.2절 우선순위와 39절 예외 절차를 따른다.

**INT-003 | 읽기 → 재사용 → 최소 변경 → 자체 검수:** 변경 전 기존 토큰·컴포넌트·유틸리티·PRD를 확인하고, 동일한 기능과 스타일을 중복 생성하지 않는다. 변경 파일·범위를 먼저 특정하고 요구하지 않은 파일을 일괄 정리하지 않는다.

**INT-004 | 범위 미확정:** 브랜드 정체성, 문구, 주 사용자 행동, 필수 기능, 운영 URL 또는 상태 전이가 불명확하면 이를 확인 필요 항목으로 표시한다. 임의로 확정하고 코드에 반영하지 않는다. 다른 부분은 합리적으로 작업 가능하면 진행한다.

**INT-005 | 동등하지 않은 규칙:** 새 프로젝트용 표준 폴더·브레이크포인트·CSS `@layer`·모듈·수치 예산 예시는 기존 HARO 구조의 자동 마이그레이션 지시가 아니다. 사용자 요청/승인 PRD 없이 대체하지 않는다.

## 31. Designer 착수 산출물과 브랜드 일관성 — MUST

**DSX-001 | 1문장 정의:** 신규 사이트 기획 시 `주제 / 핵심 대상 / 사용자가 완수할 1차 행동(Primary Job)`을 각각 한 줄로 기록한다. 승인된 PRD가 있으면 그 값을 우선한다.

**DSX-002 | 최소 디자인 계획서:** 시각 구현 전에 아래 네 가지를 짧게 적는다. 기존 사이트의 작은 수정에서는 **대상 구역에 해당하는 내용만** 갱신한다.

1. **Color:** 메인·보조 색, 배경·텍스트·상태 색의 역할과 토큰
2. **Type:** 서체·두께·제목/본문 계층 및 한글 처리
3. **Layout:** 한 문장 콘셉트, 가로 정렬 기준, 섹션 사이 관계
4. **Principles:** 이 사이트를 구별하는 1~3개 시각·인터랙션 원칙

**DSX-003 | 기억 요소의 제한:** 화면마다 모든 요소를 장식하지 않는다. 핵심 브랜드 인지 요소는 분명하게 표현하고 나머지는 절제한다. `spec-kit/AGENTS.md` PART 1의 범용적 디자인 패턴 회피 원칙을 참고하되, 승인된 HARO 시안의 표현을 금지하거나 Discovery Expedition의 디자인 값을 복사하는 규칙으로 해석하지 않는다.

**DSX-004 | 정보 중심 카피:** 문구는 장식이 아니라 이해·행동을 돕는 요소다. 한국어 문체·호칭·날짜 표기(`YYYY-MM-DD` 또는 `YYYY.MM.DD` 등)는 프로젝트 내에서 통일하고, 브랜드 톤/PRD를 우선한다. 없는 고객 후기·수상·제품 실적·사용자 수를 생성하지 않는다.

**DSX-005 | UI 상태 설계:** 상호작용 요소마다 `default`, `hover`, `focus-visible`, `active`, `disabled`, 그리고 해당 시 `loading`, `error`, `selected`, `success` 상태를 문서화한다. hover 전용 콘텐츠는 키보드·터치에도 동등하게 제공한다.

## 32. 디자인 토큰·타이포·그리드 상세 운영

**DSX-101 | 토큰 단일 원천:** 일반 색상·공통 타이포·간격·모서리·레이어·모션의 원천은 해당 프로젝트의 `tokens.css` 또는 승인된 토큰 파일로 통일한다. 컴포넌트에는 `var()`을 우선 사용한다. 이미 존재하는 `--color-ink`, `--space-4` 등의 의미 있는 변수명을 유지한다.

**DSX-102 | 의미 중심 색상:** 역할별 토큰(`primary`, `surface`, `text`, `muted`, `border`, `success`, `warning`, `danger`)을 필요한 만큼만 정의한다. 색을 순서·감정 표현의 유일 수단으로 쓰지 않는다. `--color-primary` 같은 이름은 예시이며 HARO의 기존 색상 값을 강제 교체하지 않는다.

**DSX-103 | 서체 계층:** 새 사이트에서 본문/제목의 역할 차이를 분명히 하되 서체 가족 수는 가급적 2개 이하, 실사용 굵기는 3단계 안팎을 검토한다. 특수한 브랜드 디스플레이 서체가 있으면 승인된 원본을 우선한다. 이미지 기반 텍스트가 꼭 필요하지 않다면 HTML 텍스트로 구현한다.

**DSX-104 | 한글 가독성:** 본문 약 16px을 시작점으로 하고 한글 `line-height` 약 1.6~1.8, 제목은 문맥에 맞는 약 1.2~1.35를 검토한다. 기계적인 일괄 강제는 금지하며 200% 확대, 모바일 줄바꿈, 긴 단어에서 실제 판독 가능성을 검증한다. 긴 영단어·URL에는 국소적으로 `overflow-wrap: anywhere` 등을 검토하고 한글 단어 분리를 억제한다.

**DSX-105 | 간격 체계:** 신규 공통 간격은 작은 단위의 재사용 스케일(예: 4/8/12/16/24/32/48/64...)에서 정의한다. **HARO의 실제 간격 스케일은 4/8/16/24/32/40/48/64/80/120/160px이므로, 8pt 격자 예시를 이유로 기존 값을 무단 치환하지 않는다.**

**DSX-106 | 유동 레이아웃:** 큰 틀은 컨테이너 `max-width` + 유동 폭 + Flex/Grid를 사용한다. 섹션 리듬을 한 가지 방식으로 정하고 `main > * + *` 마진과 `.section` 패딩을 중복 적용할 때 실제 총 간격을 계산한다.

**DSX-107 | 레이어·모서리:** 반경·그림자·`z-index`는 계층화한다. `z-index:99999` 등 임의 상승 금지. 모델/팝오버/고정 헤더의 겹침을 검증한다. 의미 없는 장식용 구분선·숫자 라벨·블러를 관습으로 추가하지 않는다.

**DSX-108 | 모션 토큰:** 짧은 피드백 모션과 콘텐츠 애니메이션의 목적을 구분한다. `transform`/`opacity`를 우선 사용하고 애니메이션 대상·일시정지/종료·`prefers-reduced-motion` 대응을 정의한다.

## 33. 컴포넌트 상세 동작 계약 — MUST

**CMP-001 | 버튼 3단계:** Primary(화면의 주 행동) / Secondary(보조 행동) / Tertiary(텍스트 행동)를 필요에 따라 구분한다. 동작 중 중복 클릭, 네트워크 실패, 로딩, 비활성 상태를 정의한다. 변경된 상태가 실제 기능과 일치해야 한다.

**CMP-002 | 폼:** 보이는 `<label>`과 연결 가능한 `id/for`를 사용한다. `placeholder`만으로 레이블을 대체하지 않는다. 오류는 필드 근처에 원인·해결 방법을 적고 `aria-describedby`로 연결한다. 신뢰할 수 있는 서버 검증 없는 '전송 완료' 표시는 금지한다.

**CMP-003 | 내비게이션:** 현재 페이지/섹션은 상황에 맞게 `aria-current`로 표시하고, 모바일 메뉴는 상태 표시(`aria-expanded`), Escape 닫기, 닫은 뒤 초점 처리, 비노출 링크의 탭 진입 방지까지 구현한다.

**CMP-004 | 이미지·아이콘:** 의미 이미지에는 기능/내용에 맞는 `alt`, 장식 이미지에는 `alt=""`을 사용한다. 아이콘 셋을 통일하고 SVG `currentColor`를 검토한다. 이미지에 별도 텍스트를 과도하게 합성하지 않는다. 공간 예약(`width/height`, `aspect-ratio`)으로 CLS를 줄인다.

**CMP-005 | 동적 알림:** 업데이트된 상태는 필요한 경우에만 `aria-live`로 알린다. 모달은 가능한 `<dialog>` 사용을 검토하되 기존 모달을 무단 전환하지 않는다. 초점 이동·순환·복귀·Escape·배경 상호작용을 점검한다.

**CMP-006 | 명확한 동작 안내:** '확인', 'Submit', '자세히'가 실제 목적을 모호하게 하면 구체적인 목적을 표현한다. 뒤로가기·외부 열기·전송·삭제는 사용자가 결과를 예상할 수 있어야 한다.

## 34. Developer HTML·접근성 보완 규약

**DEVX-001 | 문서 기본값:** 언어(`lang`), 인코딩, viewport, 고유 title/description, 제목 계층, 단일 `<main>`을 점검한다. 공유·검색이 중요한 운영 사이트는 canonical/OG 메타를 프로젝트별로 설정한다. 출처가 불확실한 URL은 만들어 넣지 않는다.

**DEVX-002 | 시맨틱 우선:** 클릭 행동은 `<button>`, 이동은 `<a href>`, 목록은 `<ul>/<ol>`, 표 데이터는 `<table>`을 사용한다. 서식만 맞추려 테이블을 레이아웃용으로 쓰지 않는다. `<div role="button">`을 사용하는 기존 UI는 키보드 이벤트와 상태 동기화를 검증하고 리팩터링은 승인 후 한다.

**DEVX-003 | 접근성 참조:** `aria-expanded`, `aria-controls`, `aria-current`, `aria-live`, 라벨 연결을 실제 DOM 상태에 맞춘다. ARIA는 네이티브 HTML로 같은 의미를 표현할 수 없을 때 우선 검토한다. `tabindex` 양수는 쓰지 않고 `0`/`-1`의 목적을 명시한다.

**DEVX-004 | 포커스:** 전역 `outline:none` 금지(동등 이상의 명확한 대체 포커스 제공 시만 예외). `:focus-visible`의 대비·두께·가림 여부 확인. `display:none`/`hidden`과 스크린리더 전용 `.visually-hidden`을 혼동하지 않는다.

**DEVX-005 | 화면 바깥 이미지:** 비핵심 이미지에는 `loading="lazy"` 및 필요 시 `decoding="async"`를 검토한다. 히어로의 핵심 LCP 이미지는 상황에 따라 `fetchpriority="high"` 및 선로딩을 검토하고 일괄 lazy 처리하지 않는다. 반응형 원본이 있으면 `srcset`·`sizes`·`picture`를 검토한다.

**DEVX-006 | 외부 링크:** 새 탭이 필요하면 의미를 예고하고 `rel="noopener"` 등 보안을 적용한다. `noreferrer`는 리퍼러를 숨기는 부가 영향까지 고려한다. 실재하지 않는 URL·임시 `/#`를 최종 CTA에 쓰지 않는다.

## 35. Developer CSS 구체화 — 신규 프로젝트와 기존 프로젝트 분리

**DEVX-101 | 셀렉터 명명:** 공통·재사용 가능한 블록은 BEM(`.card`, `.card__title`, `.card--featured`) 등 일관된 규칙을 사용한다. `.is-open`/`.is-active` 등 상태 클래스, `data-*`(JS·콘텐츠 후크)를 분리한다. HARO의 `.hero__*`, `.goods__*`, `data-edit-*`을 임의로 고치지 않는다.

**DEVX-102 | 선택자 복잡도:** 신규 컴포넌트는 클래스 중심으로 만들고 `id` 선택자·깊은 셀렉터 중첩·무분별한 `!important`를 피한다. **단, 실제 ID는 앵커·레이블·JS 참조로 사용 가능**하며 기존 명세와 연계한 선택자는 변경하지 않는다.

**DEVX-103 | 토큰·로딩 순서:** 재사용 속성은 토큰을 우선하고 스타일 파일의 로딩 순서를 명시한다. 신규 `@layer` 도입은 프로젝트 전체 우선순위 설계가 가능할 때만 사용한다. 기존 HARO의 `tokens → base → layout → components → box → sections` 스타일 관계를 일괄 수정하지 않는다.

**DEVX-104 | CSS 기능 범위:** 레이아웃에 Flex/Grid, 요소 간 간격은 가능한 `gap`, 논리 속성(`margin-inline`, `padding-block`, `inset-inline-start`)과 CSS `minmax`, `clamp`를 검토한다. 다만 특정 레이어의 장식·시퀀스 컷은 `position:absolute`가 필요할 수 있다. 복잡한 레이아웃 강제 전환 금지.

**DEVX-105 | 상호작용 조건:** `@media (hover:hover)` 사용을 검토하고 터치 장치에서 hover만 유효한 기능을 설계하지 않는다. `prefers-reduced-motion`, `prefers-contrast`, `forced-colors` 등을 사용자 환경에 따라 고려한다.

**DEVX-106 | 성능:** 영구적인 `will-change` 남발 금지, 스타일 변경에 의한 레이아웃 스래싱 방지, 고해상도 배경·크롭과 GPU 메모리 사용량을 함께 고려한다.

## 36. Developer JavaScript 운용 계약 — MUST

**JSX-001 | 모듈화:** 신규 프로젝트는 ES Module을 기본 검토한다. 기존 스크립트가 `defer`·IIFE 방식이면 전역 충돌 없이 해당 패턴을 유지한다. 빌드 도구 없는 환경에서는 파일 경로/로컬 서버/브라우저 동작을 확인한다.

**JSX-002 | 식별자·스코프:** `const` 우선, 재할당 필요 시 `let`, `var` 사용 회피. 전역 변수·함수의 이름 중복 방지. 함수명은 동작이 드러나는 camelCase, 상수는 UPPER_SNAKE_CASE 등을 프로젝트 관례에 맞게 사용한다.

**JSX-003 | 가독성:** 함수는 하나의 책임을 갖고, 지나치게 많은 인자·중첩을 줄인다. PDF에서 제안한 **40줄 이내·인자 3개 이하·중첩 3단계 이하**는 **권장 리팩터링 신호**로 취급하며, 기존 코드를 숫자만 맞추기 위해 쪼개지 않는다.

**JSX-004 | DOM 후크:** UI 연결은 목적별 `data-*` 선택자를 우선하고 스타일 클래스/태그명에 불필요하게 의존하지 않는다. 한 번 조회한 요소 참조는 필요한 범위에서 재사용한다. 기존 `data-edit`, `data-edit-src`, `data-goods-track` 같은 콘텐츠 연동 후크는 계약으로 보존한다.

**JSX-005 | 리스너·해제:** 동적 목록은 이벤트 위임을 검토한다. 이미 초기화된 UI에 리스너를 중복 바인딩하지 않는다. Observer·리스너·타이머는 컴포넌트 파기 시 정리한다. 스크롤은 필요 시 passive 옵션/스로틀·rAF, 가시성은 IntersectionObserver, 크기 감지는 ResizeObserver를 검토한다.

**JSX-006 | 안전한 렌더링:** 외부/사용자 데이터는 `textContent`, `createElement` 등으로 삽입한다. `innerHTML +=` 같은 누적 삽입과 신뢰할 수 없는 HTML 직접 사용을 금지한다. URL·이벤트 핸들러는 허용 범위를 검증한다.

**JSX-007 | 초기화 실패 안전:** `init*()` 함수는 대상 요소가 없는 페이지에서도 정상 종료하고 콘텐츠를 숨기거나 전체 페이지 JS를 멈추지 않아야 한다. `DOMContentLoaded` 또는 `defer`/`module` 실행 타이밍을 일관되게 결정한다.

**JSX-008 | 비동기:** `fetch` 시 `response.ok`, 타임아웃/취소(`AbortSignal` 등), 오류 UI를 고려한다. `try/catch`는 복구나 오류 전달 등 처리 의미가 있을 때 사용한다. 로딩·성공·실패·빈 데이터에 대한 화면 상태를 마련한다.

**JSX-009 | 상태 원천:** 인터랙션 상태는 데이터/상태 속성 또는 단일 변수에서 관리하고 클래스·ARIA·DOM 표시와 동기화한다. 필요하면 URL `searchParams`·hash를 북마크/새로고침 가능한 상태로 사용한다. `localStorage`는 접근 오류·용량 초과 등을 처리하고 개인정보를 저장하지 않는다.

## 37. 보안·SEO·호환성 기준 — MUST

**SEC-001 | 입력·주입:** XSS 위험 데이터 직접 삽입, `eval`, `new Function`, `document.write`, `javascript:` URL, 인라인 이벤트 문자열을 금지한다. HTML 삽입이 부득이하면 신뢰된 sanitizer를 사용하고 위험을 기록한다.

**SEC-002 | 외부 자산:** 외부 스크립트는 출처·버전·배포 경로와 필요 시 무결성(SRI)을 검토한다. 비밀정보를 HTML/JS/공개 저장소에 넣지 않는다. iframe은 유효한 제목, 필요한 경우 `sandbox`·지연 로딩을 검토한다.

**SEC-003 | 서버 협력:** 실제 서버 제어가 가능한 경우 CSP, `X-Content-Type-Options`, Referrer-Policy, CSRF 방어, HTTPS 등을 적용한다. 정적 사이트·GitHub Pages에서는 호스팅별 설정 가능 여부를 확인하고 통제할 수 없는 부분은 미검증 또는 제한으로 명시한다.

**SEO-001 | 공개 페이지:** 승인된 페이지별 title, description, canonical, 적절한 제목 구조·링크 텍스트를 갖춘다. OG 이미지/태그는 콘텐츠와 원본 자산이 확보된 경우 설정한다. robots.txt/sitemap.xml/404 페이지는 다중 페이지·공개 운영 요구사항에 맞게 추가하고 불필요한 파일을 강제하지 않는다.

**COMPAT-001 | 호환성:** 대상 브라우저/OS를 PRD에서 정의한다. 최신 주요 브라우저와 iOS/Android 터치환경에서 검증하고 미지원 기능은 점진적 향상·대체 경험을 마련한다. 문서에 제안된 브라우저 목록·기기 폭은 기본 체크리스트이지 전체 사용자 환경에 대한 검증 완료의 증거가 아니다.

## 38. 성능 예산과 증거 기반 QA — MUST

### 38.1 수치 목표의 올바른 해석

- **웹 바이탈 목표:** 75번째 백분위 실사용자 데이터 기준 LCP ≤2.5s, INP ≤200ms, CLS ≤0.1을 사용한다(기존 15절과 동일).
- **Lighthouse:** 모바일 Performance, Accessibility, Best Practices, SEO 각 **90+를 목표**로 검토한다. 다만 프로젝트 범위·외부 스크립트에 따라 달라질 수 있으므로 **측정값 없이는 통과로 보고하지 않는다**.
- **제안 예산:** JS gzip 약 100KB 이하, CSS gzip 약 50KB 이하, 이미지 1장 약 200KB 이하(히어로 약 300KB 이하)는 신규 프로젝트의 참고 목표일 뿐이다. 기존 HARO 이미지나 승인된 아트워크를 자동 삭제·화질 저하하는 근거로 사용하지 않는다. 실제 예산은 콘텐츠·화질·네트워크 조건과 측정 결과를 기준으로 합의한다.
- **이미지·폰트 최적화:** WebP/AVIF/최적 크기·`srcset`, WOFF2/필요 글리프·굵기 로드, `font-display:swap` 등을 검토하되 라이선스와 자산 실재 여부를 확인한다.
- **JavaScript 성능:** 초기 화면의 필수 로직을 가볍게 하고, 실제 필요할 때만 동적 `import()` 등을 검토한다. 긴 작업은 분할하고 스크롤·리사이즈·레이아웃 읽기/쓰기 일괄 처리를 고려한다.

### 38.2 검증 폭·환경

- 최소 대표 폭: **320 / 360 / 375 / 390 / 480 / 768 / 860 / 900 / 1024 / 1280 / 1440 / 1536 / 1920px** 중 프로젝트에 해당하는 폭과 각 브레이크포인트 **±1px**.
- `320/360/375/390/480/768/1280/1440/1536/1920px`은 대표 검증 폭 예시이며, `599/700/860/900/1024px`은 HARO 레퍼런스에서 기록한 분기다. 현재 CSS와 PRD에 맞는 폭 및 경계값을 선택한다. **이 값을 모두 별도 CSS 미디어쿼리로 만들라는 뜻은 아니다.**
- 콘텐츠 폭·텍스트 확대 200%, 키보드(포커스 이동), 모바일 터치, 마우스 hover 유무, `prefers-reduced-motion`, 낮은 네트워크/이미지 실패, GitHub Pages와 같은 배포 하위경로 검증.
- 네트워크 패널의 404, 콘솔 오류, 접근성 점검, JS 없는 상태의 핵심 콘텐츠, 캐러셀의 가로 스크롤 범위, 애니메이션 초기/완료 상태 확인.

### 38.3 작업 완료 체크리스트 — Designer / Developer

**Designer**

- [ ] 브랜드·대상·주요 행동과 화면 위계가 명확하다.
- [ ] 공통 색·타입·간격·반경·모션이 토큰에 매핑되었다(예외는 근거 기록).
- [ ] 본문/아이콘/상태의 대비와 200% 확대를 확인했다.
- [ ] 주요 컴포넌트의 default/hover/focus/active/disabled 및 필요한 로딩·오류가 정의되었다.
- [ ] 터치 타깃·키보드·반응형 전환·이미지 크롭·가로 스크롤을 점검했다.
- [ ] 장식은 정보 전달을 방해하지 않고 reduced-motion에서도 내용이 남는다.
- [ ] 실제 문구·링크·이미지의 정확성을 확인했다(가짜 후기·임시 CTA 없음).

**Developer**

- [ ] 시맨틱 구조, 유일 ID, 제목 계층, `alt`·`label`·ARIA 연결을 확인했다.
- [ ] HTML·CSS·JS 역할과 파일 경로를 유지하고 요청 외 변경이 없다.
- [ ] 인라인 이벤트·중복 전역 선언·초기화 중복·미처리 예외가 없다.
- [ ] 안전한 DOM 삽입, 폼/네트워크 오류 처리, 상태·접근성 동기화를 확인했다.
- [ ] 리소스 404·콘솔 에러·배포 경로·브레이크포인트 경계값을 확인했다.
- [ ] 이미지 치수/크롭과 캐러셀·시퀀스 애니메이션의 실패 안전 동작을 확인했다.
- [ ] 측정 가능한 성능·Lighthouse 점수는 실제 실행 결과로만 기록했다.
- [ ] 코드 변경 내역·미완료 항목·규약 예외를 최종 보고에 포함했다.

## 39. 위반·예외·버전 관리 및 사용자 보고

**GOV-001 | 적용 불가능한 MUST:** 사용자의 명시적 요청이 필수 규칙과 충돌하면 최소 위험 대안을 제시하고, 필요 시 사용자 승인 후 **규칙 ID / 사유 / 대상 파일 / 예상 영향 / 복구 방법**을 기록한다. 법적·보안상 불허되는 작업은 규약 예외만으로 허용되지 않는다.

**GOV-002 | 규약에 없는 상황:** 기존 사이트의 검증된 패턴을 우선 적용한다. 새 공통 패턴을 도입해야 할 때는 목적·재사용 범위·기존 기능 영향·테스트 범위를 적는다. 단순 편의를 위한 섹션 전체 리라이트 금지.

**GOV-003 | 배포 전 완료 보고:** 마지막에 반드시 `무엇을 바꾸었는지(파일별) / 이유 / 확인 방법 / 남은 이슈 / 규약 예외`를 간결히 보고한다. **실행하지 않은 검증은 미검증**으로 명확히 표시한다.

**GOV-004 | 규약 변경 이력:** 새 규칙은 본 문서에 추가·수정하고 날짜, 입력 자료, 규칙 근거, 충돌 해결 방침을 버전 이력에 남긴다. 편집을 이유로 과거 이력이나 이전 규칙을 조용히 삭제하지 않는다.
