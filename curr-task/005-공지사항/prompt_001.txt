수정 프롬프트 (클로드)

[역할]
너는 15년차 프론트엔드 개발자야. 첨부한 화면(HARO NOTICE 게시판)과 동일한 UI의 공지사항 게시판을 HTML/CSS/바닐라 JS로 구현해줘.

[선행 작업]
프로젝트 루트의 localstorage_to_firebase_guidelines.md를 먼저 읽고 그 지침을 최우선으로 따라. 파일이 없으면 아래 [마이그레이션 원칙]을 기준으로 해. 기존 공통 헤더/푸터와 css/common.css는 재사용해.

[개발 조건]
- 지금은 DB 없이 localStorage로 개발하고, 개발 후 Firebase(Firestore)로 마이그레이션할 예정이야.
- 기능: 목록(카테고리 탭, 10개 단위 페이지네이션) / 상세 / 글쓰기 / 수정 / 삭제
- 관리자만 글쓰기·수정·삭제 가능. 일반 사용자에게는 버튼을 숨겨.
- 필수값은 제목과 내용이고, 공백만 입력하면 막아. 작성자는 읽기 전용이야.
- 수정 시 기존 id, author, createdAt은 유지하고 updatedAt만 갱신해.
- 취소 시 변경사항이 있으면 confirm 후 이동해. 저장 전 페이지를 떠나려 하면 beforeunload로 경고해.
- 이미지 첨부는 선택 사항이야. JPG/PNG/WebP, 5MB 이하만 허용하고 미리보기와 "이미지 제거" 버튼을 넣어.
- 수정 화면에서 이미지 상태(유지 / 새 이미지로 교체 / 제거)가 저장 데이터에 반드시 반영돼야 해.
- 카테고리: 공지사항, 이모티콘, 굿즈, 사이트 소식
- 본문은 textContent로 출력해서 XSS를 방지하고, 줄바꿈은 CSS white-space: pre-wrap으로 처리해.
- 제출 중에는 버튼을 비활성화해서 중복 제출을 막아.

[마이그레이션 원칙]
1. localStorage는 js/notice-repository.js에서만 직접 호출해. 화면 JS에서는 호출하지 마.
2. 저장소 함수는 모두 Promise(async)를 반환하는 동일한 인터페이스로 만들어: getList({category}), getById(id), create(input), update(id, changes), remove(id). 나중에 이 파일 내부만 Firestore 코드로 바꾸면 되게 해.
3. 데이터 구조는 Firestore 문서 형태로 해: { id, category, title, content, author, imageUrl, createdAt, updatedAt } (날짜는 ISO 문자열)
4. 권한 체크는 js/notice-auth.js로 분리해: isAdmin(), getCurrentUserName(), requireAdmin(). 프론트 체크는 1차 방어일 뿐이고 서버 보안 규칙에서 다시 검증해야 한다는 주석을 남겨.
5. localStorage 키는 STORAGE_KEYS 상수로 관리하고, 샘플 데이터는 seedIfNeeded()로 분리해. 한 번 시드한 뒤에는 전체 삭제해도 재시드되지 않게 플래그를 둬.
6. 이미지는 canvas로 최대 1200px까지 줄여 WebP data URL로 저장하되, imageUrl 문자열 하나로만 다뤄. 나중에 Firebase Storage URL로 바꿀 수 있게 변환 함수를 notice-common.js의 fileToImageUrl() 하나로 분리해. localStorage 용량 초과(QuotaExceededError) 시에는 사용자 메시지를 보여주고 입력 내용은 유지해.
7. Firebase로 교체될 모든 지점에는 "// TODO: Firebase 교체" 주석을 달아.
8. 개발용 관리자 전환 버튼(devSetAdmin)은 목록 하단에 두고 "배포 전 제거" 주석을 남겨.

# 007. HARO NOTICE — 게시글 수정 페이지 추가

## 1. 작업 목표

기존 NOTICE 게시글 상세 화면에 `수정` 버튼을 추가하고, 클릭하면 해당 게시글의 수정 페이지가 열리도록 구현한다.

첨부한 `HARO_NOTICE_Edit_Demo.html`의 디자인과 입력 구성을 참고하되, 기존 프로젝트의 HEADER, FOOTER 및 공통 CSS를 재사용한다.

## 2. 글 수정 화면

- 기존 글쓰기 페이지와 동일한 디자인을 적용한다.
- 페이지 제목은 `NOTICE`, 화면 안내는 `공지사항 수정`으로 표시한다.
- 기존 게시글의 카테고리, 제목, 작성자, 본문 및 첨부 이미지를 불러온다.
- 제목과 본문은 편집 가능하게 하고 작성자는 읽기 전용으로 표시한다.
- 기존 이미지 확인, 이미지 변경 및 삭제 기능을 준비한다.
- 하단에 `취소`와 `수정 완료` 버튼을 배치한다.

## 3. 수정 기능

- 게시글 ID를 기준으로 기존 데이터를 불러온다.
- 제목과 본문은 필수 항목으로 검증한다.
- `수정 완료` 클릭 시 기존 게시글을 업데이트한다.
- 새 게시글을 생성하거나 기존 게시글 ID를 변경하지 않는다.
- 수정 성공 후 해당 게시글 상세 페이지로 이동한다.
- 취소 시 변경사항이 있으면 확인 메시지를 표시한다.
- 수정에 실패하면 오류를 안내하고 입력 내용을 유지한다.
- 수정할 글이 없으면 안내 후 NOTICE 목록으로 돌아갈 수 있도록 한다.

## 4. 접근 권한 및 데이터 저장

- 게시글 수정은 관리자에게만 허용한다.
- 수정 버튼 역시 관리자에게만 표시한다.
- 관리자 권한은 화면 표시뿐 아니라 실제 데이터 저장 단계에서도 검증한다.
- 현재 백엔드가 없다면 테스트 모드로 구현하되 실제 서버 저장과 구분한다.
- 추후 데이터베이스를 연결할 수 있도록 데이터 처리 로직을 분리한다.

## 5. 반응형

Desktop First 방식으로 구현한다.

- 데스크탑: 중앙 최대 너비 약 900px
- 태블릿: 화면 너비에 맞게 입력 영역과 여백 축소
- 모바일: 입력 항목 세로 배치 및 버튼 터치 영역 확보

1920px, 1024px, 768px, 390px에서 확인한다.

## 6. 기존 기능 유지

- NOTICE 목록, 검색, 페이지네이션 유지
- 기존 게시글 상세 보기 유지
- 기존 글쓰기 기능 유지
- HEADER 및 FOOTER 디자인 유지
- 다른 홈페이지 섹션은 수정하지 않음
- 프로젝트 내 기존 라우팅과 데이터 구조를 우선 재사용

작업 완료 후 `task-history/task.md`에 변경 내용을 기록하고 기존 `prompt.txt`는 수정하지 않는다.

**최종 목표:** NOTICE 게시글 상세 화면에서 수정 버튼을 누르면 기존 내용이 입력된 수정 페이지가 열리고, 수정한 내용을 저장하면 같은 게시글의 상세 화면에서 변경사항을 확인할 수 있도록 구현한다.
