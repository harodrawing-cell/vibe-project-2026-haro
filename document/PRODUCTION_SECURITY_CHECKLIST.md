# 운영 보안 검증 및 관리자 점검 절차

작성: 2026-11-08. 이 문서는 운영자가 수행할 절차다. 이번 문서 작성으로 규칙 게시, 데이터·계정 변경, Push, React 배포를 실행하지 않았다.

## 1. 관리자 권한의 읽기 전용 감사

1. 신뢰된 Google 계정으로 Firebase Console의 **haro-web-project / Firestore Database / (default)**를 확인한다. 앱에서 관리자라고 표시되는 사실을 승인 증거로 삼지 않는다.
2. Firestore 데이터 탭에서 `users`의 `role == "admin"` 문서와 `admins`의 `enabled == true` 문서를 각각 조회한다. 두 결과의 **UID 합집합**이 실제 관리자 후보 목록이다. 문자열 `"true"`와 불리언 `true`를 혼동하지 않는다.
3. 후보마다 Authentication 사용자 목록의 UID와 대조하고 계정 존재·사용중지 상태를 확인한다. `users` 프로필 유무도 확인한다. 특히 admins만 있는 계정은 관리자 판정은 되더라도 답변 저장에 필요한 users.name이 없어 기능이 실패할 수 있다.
4. 별도로 승인된 운영자 명단·업무 기록·소유자 확인과 교차 검증한다. 전체 공개 기간에 기록된 이름·생성일·role 자체는 신뢰할 수 있는 증거가 아니다. 감사 로그가 있으면 참고하되 없다고 정상으로 판단하지 않는다.
5. 접근을 제한한 저장소 밖 감사표에 UID, users.role, admins.enabled, Auth 상태, 승인 근거, 판정, 점검자·시간만 최소 기록한다. 판정은 승인됨/확인 필요/승인 근거 없음/Auth 없음으로 나눈다. 토큰·비밀번호·서비스 계정 키는 기록하지 않는다.

새 규칙은 향후 클라이언트의 관리자 승격을 막지만 과거에 위조된 권한을 자동 제거하지 않는다. 관리자 Firestore 플래그 감사와 별도로 Firebase/Google Cloud IAM의 프로젝트 접근자·서비스 계정도 신뢰된 소유자가 점검해야 한다. 서버 자격 증명은 이 클라이언트 규칙과 다른 권한 경로다.

## 2. 승인되지 않은 관리자 발견 시

즉시 삭제하지 않는다. 해당 UID의 두 권한 문서와 승인 근거를 안전하게 백업하고, 소유자가 오인 여부를 확인한다. 현재 상태·변경 대상·복원 방법·정상 관리자의 접근 유지 방법을 정해 변경 승인을 받는다.

승인된 권한 회수에서는 **users.role과 admins.enabled 양쪽**을 처리해야 한다. 예를 들어 일반 회원으로 유지할 대상은 role을 user로, enabled를 false로 바꾸는 방식으로 데이터를 보존할 수 있다. 한쪽만 해제하면 다른 경로로 계속 관리자다. 이 조치는 회원 계정 삭제와 구분한다. 정상 사용자의 글·프로필·예약문서를 연쇄 삭제하지 않는다. 복원 시에도 위조된 권한을 그대로 되돌리지 않도록 재승인한다.

계정 침해가 의심되면 해당 UID의 Auth 사용중지·refresh token 회수를 별도 승인 범위로 검토한다. **사용중지나 refresh token 회수만으로 기존 ID token이 즉시 모두 무효화된다고 가정하지 않는다.** 현재 관리자 권한 경로 해제와 서버 읽기 재검사가 필요하다. 강등 후에도 본인이 쓴 비공개 질문의 작성자 권한은 남는 것이 정상이다. 기존에 이미 읽은 정보는 회수할 수 없다. [Firebase 세션 관리](https://firebase.google.com/docs/auth/admin/manage-sessions)

조치 후 승인 관리자 정상 접근, 해당 UID의 타인 비공개 질문·관리자 답변 접근 거부, 일반회원 본인 질문 권한을 새 브라우저 세션과 서버 요청으로 재확인한다. 이번 작업에서는 위 조치를 실행하지 않았다.

## 3. Console 전체 규칙과 로컬 후보 비교

Console Rules 탭에서 **현재 게시된 버전**인지 먼저 확인한다. 미게시 편집 내용을 백업본으로 착각하지 않는다. 프로젝트·DB·게시 시각을 기록하고 전체 코드를 저장소 밖의 별도 파일(예: `C:\Temp\haro-rules\deployed-before.rules`)로 UTF-8 저장한다. 로컬 후보를 그 파일에 덮어쓰지 않는다.

VS Code의 파일 비교 기능 또는 설치된 경우 다음 명령으로 전체 차이를 확인한다. 이 명령은 읽기 전용이다.

```powershell
code --diff "C:\Temp\haro-rules\deployed-before.rules" ".\firebase\firestore.rules"
Get-FileHash -LiteralPath .\firebase\firestore.rules -Algorithm SHA256
```

현재 검증 후보 SHA256은 `9b5948a06c5f36d2acb18a33f013ba875f5118c7a324b3680924159436d8ddec`다. 줄바꿈·인코딩 차이로 해시가 달라도 의미가 같을 수 있으므로 Console 복사본은 텍스트 비교도 한다. Console 원문을 확보하지 않았으므로 **실제 운영 규칙과의 정확한 차이는 아직 확정하지 않았다.**

이전 로컬 후보가 운영과 동일하다면 예상 차이는 usernames/emails의 get 조건 강화와 minimalReservation 함수 추가다. 형식에 맞는 키만 허용하며 기존 문서는 uid 문자열 한 필드만 있어야 한다. 이외 차이가 있으면 게시 전 검토한다. NOTICE/users/admins/Q&A 블록, 전체 경로 허용 잔류 여부를 모두 확인한다. 다른 allow가 허용하면 마지막 deny로 상쇄되지 않는다.

게시 전 기존 예약문서의 추가 필드·누락/빈 UID를 관리 권한으로 읽기 전용 점검한다. 오염된 문서는 새 규칙에서 중복 확인이 거절될 수 있으므로 데이터를 자동 정리하지 말고 별도 처리안을 정한다. 현재 규칙 전체를 교체하고 Publish를 누르는 것은 운영자가 승인한 시점에만 수행한다. 게시 후 전체 코드를 다시 저장·비교하고 시각을 기록한다. 문제가 생겨도 예전 무조건 전체 허용 규칙으로 되돌리지 않는다.

규칙은 새 요청에 최대 약1분, 활성 리스너에는 최대10분까지 반영이 걸릴 수 있다. 새 세션·새 서버 요청으로 확인하고 그 이후에도 실패하면 전파 탓으로 단정하지 않는다. [Firestore 규칙 게시 안내](https://firebase.google.com/docs/firestore/security/get-started)

## 4. 게시 후 운영자 수동 검증

아래 쓰기 검증은 실제 데이터를 생성·변경한다. **운영자가 별도로 동의한 전용 테스트 계정·게시글에만** 수행한다. 기존 회원·기존 게시글은 변경하지 않는다. 테스트 데이터도 자동 삭제하지 말고 테스트 대상으로 합의한 질문 삭제만 실행한다. 관리자 계정은 승인된 기존 계정을 사용하며 앱에서 승격시키지 않는다.

사이트 배포 없이 `http://127.0.0.1:5173/react.html` 또는 `http://127.0.0.1:4173/`에서 운영 Firebase를 대상으로 검사할 수 있다. 서버 실행 상태와 실제 프로젝트 연결을 먼저 확인한다. 비로그인 G, 작성자 A, 다른 일반회원 B, 승인 관리자 M을 별도 브라우저 프로필로 분리한다. 시크릿 창 여러 개가 세션을 공유할 수 있으므로 서로 다른 세션인지 확인한다. DevTools Network의 서버 응답과 새로고침 결과를 함께 기록하고 캐시 화면만으로 성공 판정하지 않는다. 토큰·비밀번호·본문을 보고서에 복사하지 않는다.

타인 쓰기·role/authorUid 위조 같은 음성 검사는 성공할 경우 실제 피해가 날 수 있다. 운영에서는 대상 전용 문서·허용된 검사 범위를 먼저 정하고, 공격성 임의 요청은 수행하지 않는다. 이미 통과한 Emulator 음성 검사와 운영 실검사를 구분해 기록한다.

읽기 전용 자동 검사는 `node tests/react-final-readonly.cjs`로 실행할 수 있다. 환경의 브라우저·네트워크 요구사항이 충족되어야 한다. 결과의 실행 시각과 authGuest, notice, qna.privateMetadataMasked, privateDetail/privateAnswer.unauthenticatedREST를 확인한다. 이 검사는 운영 가입·쓰기·실계정 로그인 성공을 증명하지 않는다.

기록 양식: 실행시각/Console 게시버전/앱 주소/계정 구분(G,A,B,M)/검사 항목/기대결과/실제 서버 응답/통과·실패·미실행/개인정보를 제외한 증거 위치. 실패하면 운영 배포를 보류하고 원인을 수정한 뒤 해당 권한 조합을 재검사한다.

## 6. 별도 개선 과제 AUTH-PRIVACY-01

유효한 아이디/이메일의 정확한 키를 추측하면 가입 여부 및 UID를 읽을 수 있다. 형식 제한·uid 단일 필드 검사는 이 위험을 제거하지 않는다. Firestore 공개 예약문서 읽기를 없애고 신뢰 서버의 최소 응답 API, 요청 제한·반복 탐지, 이메일 소유 확인 및 일반화된 안내를 설계한다. 공개 아이디 중복 기능 자체의 존재 여부 신호는 요구사항과 함께 판단한다.

완료 기준: 비로그인 및 다른 회원이 직접 예약문서/목록/UID를 읽을 수 없음, API가 UID를 반환하지 않음, 열거 방지 정책 검증, 가입·중복 처리·부분 실패 복구 회귀 통과. 이메일 해시화만으로 완료 처리하지 않는다. 담당·일정·비용·배포 및 잔여 위험 수용 여부는 아직 미정이며 이번에는 구현하지 않았다.
